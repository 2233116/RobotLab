ESP32 + Thonny 卡顿急救与排查手册

1. 使用范围

本文用于排查 ESP32 使用 MicroPython 和 Thonny 时出现的以下问题：

- Thonny 无法中断程序；
- Shell 不再出现正常提示符；
- 程序启动后立即卡住；
- ESP32 与电脑串口通信异常；
- 电机运行时偶发卡顿或断联。

不同问题可能具有不同根因。应先恢复基本通信，再逐步判断是软件运行、串口通信、电源还是硬件连接问题。

2. 第一阶段：尝试恢复 Thonny 与 ESP32 通信

2.1 尝试中断程序

1. 在 Thonny 中尝试停止正在运行的程序。
2. 如果普通停止无效，可以尝试使用 Thonny 支持的中断快捷键，例如 "Ctrl + F2"，具体以当前版本的快捷键设置为准。
3. 等待 Shell 是否重新出现 MicroPython 提示符 ">>>"。

连续点击停止按钮不一定能够解决问题。如果底层串口已经失去响应，反复操作也可能没有效果。

2.2 重新连接 USB

如果仍无法中断：

1. 断开 ESP32 的 USB 连接。
2. 等待几秒。
3. 重新连接 USB。
4. 在 Thonny 中确认选择了正确的串口。
5. 尝试重新连接并观察 Shell 是否恢复。

重新连接 USB 可能恢复串口通信，但如果程序每次启动都会再次卡住，还需要进一步排查自动运行代码。

2.3 程序一启动就卡住

如果 ESP32 在启动时自动执行了有问题的 "main.py" 或其他启动代码，可以尝试通过开发板的 BOOT 和 EN/RST 按钮进入适合当前板卡的恢复状态。

常见操作思路是：

1. 按住 BOOT。
2. 按一下 EN/RST，然后松开 EN/RST。
3. 尝试让板卡进入不会立即执行原程序的状态。
4. 在 Thonny 中尝试中断并恢复 Shell 通信。
5. 如果能够正常进入 ">>>"，检查并修复或移除导致卡住的启动代码。

**注意：**不同 ESP32 开发板的按键、电路和启动方式可能不同，上述操作不保证对所有板卡都有效。如果没有恢复，不要连续盲目操作，应先确认具体开发板型号和启动方式。

恢复通信后，应先保存需要保留的代码，再修改导致卡住的程序。

3. 第二阶段：排查运行电机时的随机卡顿

如果软件通信已经恢复，但程序在运行电机时偶发卡顿，应按以下方向逐项检查。

3.1 检查串口引脚是否冲突

经典 ESP32-WROOM-32 常见的 UART0 引脚为：

- GPIO 1：TX；
- GPIO 3：RX。

如果程序使用这些引脚连接电机控制信号或其他外设，可能影响串口通信。

排查时应确认实际板卡、代码和接线，不要只根据默认引脚推测。部分板卡或程序可以重新配置 UART 引脚，但需要明确实际使用方式。

3.2 检查供电与电压跌落

观察问题是否总发生在电机启动、反转或加速的瞬间。

这些操作可能带来较大的瞬时电流需求。如果供电能力不足、线路压降过大或地线连接不可靠，可能造成 ESP32 重启、通信异常或程序行为异常。

排查要点：

- 不要用 ESP32 的普通 GPIO 或不适合的供电脚直接驱动电机。
- 使用符合电机与驱动板要求的独立动力电源。
- 确认 ESP32 和电机驱动系统的信号参考地连接正确；采用共地方案时，确认 GND 连接可靠。
- 检查电池、接插件、导线和驱动板供电端是否存在松动。
- 如果条件允许，测量电机启动瞬间的供电电压，而不是只检查静态电压。

仅凭“电机启动时发生卡顿”还不能直接断定是电压跌落，需要结合实际测试确认。

3.3 检查接线虚接与电气噪声

电机和编码器工作时，松动的杜邦线、面包板接触不良以及电机产生的电气噪声，都可能造成信号异常。

排查要点：

- 检查编码器 A/B 信号线和电源线是否松动。
- 检查驱动板控制线与 ESP32 的接线是否牢固。
- 检查电机电源线与编码器信号线是否存在不合理的布线或干扰耦合。
- 在断电后检查端子和导线连接，避免带电摇动线路。
- 如有条件，使用示波器或逻辑分析工具观察异常时的信号。

有时重新插拔导线后问题暂时消失，并不能证明根因已经找到；还应确认修复后能否稳定复现和通过测试。

3.4 电容与其他抑制措施

在合适的电路位置增加电容，有时可以改善电源瞬态或部分电气噪声问题，但具体效果取决于电路、负载和干扰来源。

不要把“并联一个 100 μF 电容”当成通用解决方案。选择电容前应确认：

- 所在电源轨的电压范围；
- 电容极性与耐压；
- 驱动板厂商建议的去耦方式；
- 实际问题是电源波动还是信号干扰。

电容不能替代正确的供电设计、布线、接地和必要的电机抑制措施。

4. 第三阶段：排查软件主循环卡顿

如果串口和供电基本正常，应检查程序是否有过多的阻塞操作或无效重复工作。

常见检查项：

- 是否存在长时间阻塞的循环或等待；
- 是否有过于频繁的串口打印；
- 是否在每次主循环迭代中重复执行不必要的计算；
- 是否有变量未按预期更新，导致控制器重复使用旧值；
- 是否有异常分支让某一侧控制器长期得不到调用；
- 是否有程序异常导致控制输出长期饱和。

排查时优先保留必要的状态记录，避免一次加入大量打印，反而改变原有运行时序。

5. 案例：双电机闭环中的高频打印

5.1 现象

在双电机闭环控制重构期间，曾在主循环中高频打印左右电机速度、目标速度和 PWM 等变量。

调试时观察到 PWM 输出偏大、速度读数重复等现象。减少主循环中的打印，并将打印移动到实际执行 PID 更新的分支后，运行表现有所改善。

5.2 可能的解释

Encoder 只会在新的有效测速窗口结束后更新速度变量。如果在紧密循环中反复打印，就可能多次输出同一个速度值。

类似地，PWM 通常只会在控制器实际执行 PID 更新时改变。因此，高频日志中连续出现相同数值，并不自动意味着编码器没有脉冲或控制器没有运行。

频繁的串口输出会增加系统负载，也可能影响程序执行时序。但目前的实验还不能证明 "print()" 导致了编码器中断丢失。

5.3 当前结论

减少不必要的高频打印是一项有效的调试改进；本次修改后系统表现有所改善。

但具体异常根因仍未被独立验证。不能把本次现象直接推广为所有 ESP32 卡顿的共同原因。

5.4 后续调试方式

- 将日志放在实际的测速更新或 PID 更新分支中。
- 优先输出必要的状态，而不是在紧密循环中重复输出全部变量。
- 对比修改前后的运行结果时，尽量保持其他条件不变。
- 分别记录启动阶段、稳态阶段和异常发生时的表现。
- 如果问题仍然存在，再独立检查编码器信号、电源、引脚冲突和执行时序。

6. 推荐排查顺序

出现卡顿时，建议按以下顺序执行：

1. 恢复通信：尝试中断程序，必要时重新连接 USB。
2. 检查启动代码：确认是否由自动运行的程序导致再次卡住。
3. 检查串口与引脚：确认 UART 和外设接线没有冲突。
4. 检查供电：观察电机启动或反转时是否出现电压异常。
5. 检查连接与噪声：确认编码器、驱动板和电源连接可靠。
6. 检查程序负载：减少无必要的高频打印，检查阻塞和变量更新逻辑。
7. 逐项验证：每次只改变一个因素，保留修改前后的现象和结果。

7. 长期排查原则

- 先恢复基本通信，再分析根因。
- 不要同时修改程序、接线、供电和参数。
- 将观察到的相关性与已经证实的因果关系区分开。
- 硬件改动前先断电，确认电压、极性和接线。
- 先保存已验证的代码基线，再做实验性修改。
- 修复后进行可重复的短时测试，确认问题不再出现。
