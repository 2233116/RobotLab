PID 模块化与 dt 工程化

1. PID 模块化结构

PID 从主程序中独立出来，由 "PID" 类负责控制量计算。

当前接口：

pid.update(current_speed, dt, target_speed)

PID 内部持有：

- "kp"
- "ki"
- "kd"
- "integral_error"
- "previous_speed"
- 积分上下限

PID 外部提供：

- "current_speed"：当前测速结果；
- "target_speed"：外部控制目标；
- "dt"：本次 PID 更新对应的实际时间间隔。

控制调度不由 PID 类负责。PID 只负责根据输入参数和自身内部状态计算控制量。

2. 当前模块职责

当前单侧电机速度闭环的模块职责如下。

Encoder

负责获取电机实际机械速度，并提供本次测速对应的 "elapsed_time"。

PID

负责根据当前速度、目标速度和时间间隔计算控制量，维护自身的积分、历史状态等数据。

Motor

负责将控制器输出转换为电机驱动所需的 PWM 指令。

MotorController

负责组织单侧电机的闭环控制流程，包括：

- 持有对应的 Motor、Encoder 和 PID 对象；
- 保存该侧的目标速度；
- 统计有效测速更新次数；
- 累计测速实际经过的时间；
- 决定何时调用 PID；
- 将 PID 输出发送给对应电机。

Main

负责创建左右两侧的对象，并在主循环中分别调用左右控制器的 "update()"。

当前主循环的基本结构：

while True:
    left_motorcontroller.update()
    right_motorcontroller.update()

主循环负责调用控制器，但不再直接重复编写左右两侧的测速计数、时间累计、PID 更新和 PWM 输出流程。

3. MotorController 的当前控制流程

当前 "MotorController" 的主要成员包括：

- "motor"
- "encoder"
- "pid"
- "target_speed"
- "control_count"
- "dt"
- "pwm"

每次调用 "update()" 时，先检查：

self.encoder.update()

只有当 Encoder 产生新的有效测速结果时，控制器才进行本轮计数和时间累计。

当前流程如下：

1. 获得新的有效测速结果。
2. "control_count" 增加一次。
3. 将本次 "encoder.elapsed_time" 累加到 "dt"。
4. 当 "control_count" 达到 3 次时，执行一次 PID 更新。
5. 将累计时间作为本次 PID 更新的 "dt"。
6. 使用当前速度、累计时间和目标速度调用 PID。
7. 将 PID 输出发送给对应电机。
8. 清零计数和累计时间，为下一控制周期做准备。

左右控制器分别维护自己的计数、累计时间和 PID 状态。不能假设左右编码器一定在同一轮主循环中同时更新。

当前实现使用最近一次有效测速得到的 "current_speed" 作为本次 PID 更新的速度输入，并没有对三次速度读数再做一次平均。这是当前基线的实际行为，后续若要更改，应作为独立改动验证。

4. dt 的工程化

4.1 原始方式

早期实现直接使用固定数值：

pid.update(current_speed, 0.6, target_speed)

其中 "0.6" 是人为假定的控制周期。

如果真实的两次 PID 更新之间隔并不总是 0.6 秒，这个固定值就不能准确代表实际经过的时间。

4.2 当前方式

当前控制器累计 Encoder 每次有效测速更新对应的实际时间：

self.dt = self.dt + self.encoder.elapsed_time

累计到三次有效测速更新后：

dt = self.dt

再调用：

self.pid.update(
    self.encoder.current_speed,
    dt,
    self.target_speed
)

这里的 "dt" 表示本次 PID 更新所对应的实际累计时间，而不是单次 Encoder 测速窗口的时间。

完成本次控制更新后，控制器将采样计数和时间累计值清零。

4.3 注意事项

- "dt" 应与 PID 实际更新之间的时间间隔相匹配。
- 不能因为每次测速窗口约为 0.2 秒，就直接认定 PID 周期严格为 0.6 秒。
- 实际控制间隔可能受到测速更新时间、主循环执行情况和系统负载影响。
- 若以后改成硬件定时器固定周期调度，应重新核对 PID 的执行周期与传入的 "dt" 是否一致。

5. 固定周期与非固定周期

如果控制器由可靠的硬件定时器严格保证固定周期，例如：

"10 ms → PID → 10 ms → PID → 10 ms → PID"

则可以使用固定的：

dt = 0.01

如果 PID 的执行间隔可能变化，则应使用实际经过的时间作为 "dt"。

因此，"dt" 是由控制系统的调度方式决定的，不存在 PID 必须自己计算或必须由外部传入的绝对规则。关键在于时间参数必须符合控制器实际执行方式。

6. 当前真机验证基线

6.1 已验证参数

当前使用的 PID 参数：

- "Kp = 0.25"
- "Ki = 0.3"
- "Kd = 0.05"

此前双电机独立闭环测试中，目标速度为 100 RPM 时，左右电机均能稳定运行在目标附近。

已有记录包括：

- 左侧稳定速度约 99–101 RPM；
- 右侧稳定速度约 100–102 RPM；
- 左侧稳定 PWM 约 44；
- 右侧稳定 PWM 约 36。

不同测试条件下的实际结果可能有所变化。这组参数是当前硬件、测速方法和控制周期下的已验证基线，不是通用最优参数。

6.2 MotorController 封装后的初步测试

2026-10-22，完成了双侧闭环调度逻辑向 "MotorController" 的封装。

目标速度设为 90 RPM 时，启动初期出现过较大的速度波动，随后速度读数多数收敛到约 88–94 RPM。

这是初步观察记录，尚未完成系统化的阶跃响应测试，不能仅凭这组读数判断动态性能已经全部验证通过。

7. 高频打印排查记录

重构期间，曾在主循环中高频打印速度、目标速度和 PWM 等变量。随后观察到运行表现异常，包括 PWM 输出偏大以及速度读数重复。

减少主循环中的高频打印，并将调试输出移动到实际执行 PID 更新的分支后，系统表现有所改善。

需要注意：

- "current_speed" 只会在新的有效测速结果产生后更新。
- "pwm" 通常只会在实际执行控制更新时改变。
- 如果在紧密循环中反复打印，可能会连续输出相同的旧值。
- 高频串口输出会增加系统负载并影响执行时序，但现有观察不能证明它一定造成了编码器中断丢失。

因此，目前的结论是：减少不必要的高频打印是有效的调试改进，但具体异常根因尚未被独立验证。

8. 当前工程原则

1. 成熟方案先跑通，改进方案先对照验证。
2. 未经真机验证，不替换已验证基线。
3. 模块化改造期间，尽量保持硬件连接、PID 参数和控制周期等条件不变。
4. 不同时改变多个变量，以免无法判断问题来源。
5. 将启动瞬态与稳态表现分开记录。
6. 不把相关性直接当作因果关系。
7. 调试输出应服务于实际控制事件，避免在紧密循环中无差别打印全部变量。

9. 下一阶段

下一阶段从基础闭环运行转向动态响应验证。

在硬件连接、PID 参数和控制方式保持不变的条件下，依次测试：

"90 RPM → 60 RPM → 120 RPM"

分别观察左右电机的：

- 目标速度与实际速度；
- 目标改变后的响应方向；
- 响应时间与稳定时间；
- 超调情况；
- 稳态误差与波动；
- PWM 的变化过程。

完成测试并分析数据前，不因启动初期的波动直接修改 PID 参数。

此前提出的“基础 PWM + P 修正”属于备选控制思路。当前优先验证已经运行的闭环控制器，而不是在尚未完成动态测试前再次切换控制架构。
