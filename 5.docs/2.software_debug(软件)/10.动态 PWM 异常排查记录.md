核心结论
本次电机闭环控制中“动态 PWM 偶发掉速至 0 RPM”的故障已成功定位并解决。
真实根因： 并非硬件过载、驱动器故障或电池欠压保护，而是 Motor.set_speed() 软件实现中的逻辑缺陷。原代码在每次调速时都会先将两路 PWM 强制清零（duty_u16(0)），在频繁的动态调速（如 P 控制）下，导致 MicroPython 底层 PWM 外设寄存器状态与软件状态脱节（实际 PWM 输出变为了 0，但软件变量记录仍为非 0），且受到 if speed == self.speed: return 保护逻辑的阻碍无法恢复。
排查与推导链条
排查遵循了“先证明故障存在 \rightarrow 再证明触发条件 \rightarrow 最后验证底层逻辑”的递进路线：
 * 排除单纯的硬件驱动/固定点故障
   * 固定 PWM 对照测试：长时间稳定运行，证明电机、编码器、供电及驱动器的基础连续驱动能力无异常。
   * 动态 PWM 测试（45↔50 / 50↔60）：均能复现掉速至 0 的现象，证明问题由“动态调速过程”本身触发，与算法类型无关（纯动态 PWM 和 P 控制均会触发）。
 * 排除驱动器 Hardware 故障与欠压断电
   * 更换驱动器（ZK-BM1 \rightarrow DRV8870）后故障依然存在，排除单款驱动芯片损坏或过热的可能。
   * 测得故障发生时，ESP32 对应的驱动输入引脚 IN1 = 0V，DRV8870 输出 OUT = 0V。证明是 MCU 主动停止了输出，而非驱动器芯片因欠压/过流保护自主关断。
 * 定位 MCU 外设与底层代码
   * 抓取故障瞬时日志发现：软件记录 motor_speed ≈ 51，但读取 MicroPython 底层硬件寄存器 motor.pwm.duty_u16() 返回值却为 0，证实“软件记录值与硬件实际输出脱节”。
   * 溯源 Motor.set_speed() 源码：发现调速逻辑为：PWM1(0) -> PWM2(0) -> PWM1(new_duty)。同向调速时插入的瞬间清零动作导致了状态异常；后续又因 speed == self.speed 的拦截，导致无法再次写入正常 duty。
解决方案与效果验证
 * 逻辑优化：修改调速逻辑，同向调速时仅关闭反向 PWM 通道，不再对正向通道执行“先清零再设值”的操作；仅在 speed == 0 或方向切换时才清零。
 * 验证结果：在长时间大批量的动态 P 控制测试（目标 100 RPM）下，duty_u16 始终维持正常数值，电机未再出现一次掉速至 0 RPM 现象，故障彻底消除。
工程经验沉淀
 * 别被软件状态欺骗：软件变量（如 self.speed = 51）只代表“曾下发过的命令”，不代表 MCU 硬件寄存器或外设引脚的真实电平，排查问题必须以物理信号/外设读数为准。
 * 区分静态与动态逻辑：静态运行正常（固定 PWM）不能代表动态切换逻辑无瑕疵，状态切换（Transition State）往往是嵌入式并发与外设控制中最容易出 Bug 的环节。
 * 推导链条闭环：从物理电机停转 \rightarrow 驱动器输出 0V \rightarrow MCU 引脚 0V \rightarrow 外设寄存器 0 \rightarrow 源代码逻辑漏洞，完成了完整的硬件到软件的逐层递进定位。
当前实验状态与下一阶段
目前系统底层驱动已稳定，在设定目标转速为 100 RPM、base_pwm ≈ 50%、Kp = 0.1 的动态 P 控制下，系统收敛状态如下：

 * 实际转速：~90 RPM
