RobotLab 动态 PWM 偶发掉速至 0 RPM 完整排查与定位归档
一、 故障现象与初始假象
在电机闭环控制（ Base + P 控制及纯动态 PWM）测试中，出现间歇性故障：
 * 固定 PWM（静态）：能够持续稳定运行（如固定 50% PWM，电机、编码器、驱动器均正常）。
 * 动态 PWM（调速）：无论是 P 控制算法，还是简单的周期性 PWM 动态切换（如 45% ↔ 50%、50% ↔ 60%），运行一段时间后均会偶发出现转速突然快速下降并最终归零（0 RPM）。
 * 启动恢复：停转后再次下发新的 PWM 命令，电机能够重新启动。
二、 逻辑递进排查过程
采用“排除算法因素 \rightarrow 排除硬件驱动/电源 \rightarrow 沿信号链向上追溯”的递进路线：
[故障现象] 动态调速下电机偶发掉速至 0
   │
   ├── 1. 算法排除：去掉 P 控制，仅做纯动态 PWM 切换（52轮编号实验）
   │      └── 结果：仍偶发掉速（第5轮、第26轮异常），排除 P 算法问题，确定由“动态调速”触发。
   │
   ├── 2. 硬件驱动排除：驱动器从 ZK-BM1 更换为 DRV8870
   │      └── 结果：现象相同，排除单款驱动芯片自身发热、损坏或特定保护。
   │
   ├── 3. 电源压降排查：测量电池电压（满电 12.45V / 运行 12.25V / 重启 12.15V）
   │      └── 结果：虽存在负载压降，但后续测得驱动输入已为 0V，排除驱动器自主欠压保护。
   │
   ├── 4. 信号链追溯：测量物理电平信号
   │      ├── DRV8870 输出端 (OUT) ≈ 0V
   │      └── ESP32 控制输入端 (IN1) = 0V
   │      └── 结论：驱动器没输出是因为 MCU 根本没有下发 PWM，问题在 ESP32 软件/外设层。
   │
   └── 5. 底层外设寄存器对比：打印硬件实际 duty
          ├── 软件记录状态：motor_speed ≈ 51
          └── 寄存器实测状态：motor.pwm.duty_u16() == 0
          └── 结论：软件记录值与硬件 PWM 外设实际输出脱节。

三、 根因分析与代码漏洞
问题定位在 Motor.set_speed() 类的更新逻辑与保护逻辑交织：
漏洞 1：调速过程中的“双路强制清零”
# 原始缺陷逻辑
if speed > 0:
    self.pwm1.duty_u16(0)  # 每次调速，先将两路全部清零
    self.pwm2.duty_u16(0)
    self.pwm1.duty_u16(
        int(speed_1 / 100 * 65535)
    )  # 再重新写入新 PWM

 * 缺陷：即便只是做微小的同方向调速（如 50% \rightarrow 51%），代码也会强制插入一次 duty = 0 的操作。在频繁调速时，该密集清零序列触发 MicroPython 底层 PWM 外设状态脱节，导致实际输出被置 0。
漏洞 2：防重设逻辑导致“死锁”
# 拦截逻辑
if speed == self.speed:
    return

 * 缺陷：当底层硬件 duty 异常变为 0 后，软件内部记录的 self.speed 仍为 51。后续算法再次传入 51 时，直接被此语句拦截并 return，导致无法重新向硬件写入正确的 duty，电机彻底停转。
四、 修复方案与效果验证
1. 代码修改原则
 * 同向调速：直接更新当前方向 PWM，只清零反向通道。
 * 方向切换 / 停止：才执行对应通道关闭或双路清零。
# 修改后核心逻辑
if speed > 0:
    self.pwm2.duty_u16(0)  # 仅关闭反向通道
    self.pwm1.duty_u16(int(speed_1 / 100 * 65535))  # 直接更新正向通道
    self.is_running = True
elif speed < 0:
    self.pwm1.duty_u16(0)  # 仅关闭正向通道
    self.pwm2.duty_u16(int(speed_1 / 100 * 65535))  # 直接更新反向通道
    self.is_running = True
elif speed == 0:
    self.pwm1.duty_u16(0)
    self.pwm2.duty_u16(0)
    self.is_running = False

2. 验证结果
在目标转速 ~100 RPM、Kp = 0.1 的长时间大批量动态 P 控制测试中：
 * motor.pwm.duty_u16 输出恢复正常连续性；
 * 未再出现 IN1 = 0V 及掉速至 0 RPM 的现象；
 * 手动发送 KeyboardInterrupt 即可正常中断测试，故障消除。
五、 工程经验总结
 * 软件变量 \neq 硬件实际状态：self.speed = 51 只代表软件下发过的指令，不代表底层外设寄存器或引脚电平的物理真实值。
 * 区分静态与动态状态转换：固定 PWM 运行正常不能证明动态调速正常，状态切换（Transition State）序列是嵌入式外设控制中最容易出 Bug 的环节。
 * 推导链条闭环：从物理停转 \rightarrow 输出 0V \rightarrow 引脚 0V \rightarrow 寄存器 0 \rightarrow 源码逻辑漏洞，完成了自顶向下的完整物理验证。
六、 当前实验 Baseline（为后续 PID 留存）
 * 目标转速：100 RPM
 * 基础 PWM：~50%
 * 控制参数：K_p = 0.1
 * 实际稳态：~90 RPM（稳态误差 \Delta v \approx 10\text{ RPM}）
 * 结论：系统底层已稳定，当前残余误差为纯 P 控制无积分环节的物理必然现象，后续可作为引入积分（I）控制的对比 Baseline。
