## 一、今日完成内容

### 1. 完成 `MotorController` 类的封装

将原来主循环中重复的左右电机控制流程封装到 `MotorController` 类中。

控制器通过构造函数接收：

- `motor`：负责电机输出；
- `encoder`：负责获取编码器测速结果；
- `pid`：负责速度闭环调节；
- `target_speed`：目标转速。

控制器内部使用：

- `control_count`：累计有效测速次数；
- `dt`：累计控制周期；
- `pwm`：保存最近一次 PID 输出。

当前控制流程为：

1. 调用 `encoder.update()`；
2. 检查是否产生新的有效测速结果；
3. 累计三次测速及对应时间；
4. 调用 PID 计算新的 PWM；
5. 将 PWM 输出给对应电机。

左右电机分别拥有独立的 `Motor`、`Encoder`、`PID` 和 `MotorController` 对象。

### 2. 排查重构后的异常

重构初期出现过：

- PWM 持续达到 100；
- 测得转速接近 0 RPM；
- 串口出现大量重复输出。

检查确认，原来的 `motor.py`、`encoder.py`、`pid.py` 没有修改；原始双电机主循环可以正常运行。

随后将高频打印改为只在 PID 实际执行调节时输出。调整后，系统恢复稳定。

**排查结论：** 高频打印与异常表现存在关联，降低打印频率后运行表现改善。但尚未证实具体原因，尤其不能直接认定是编码器中断丢失导致异常。

### 3. 理解调试输出与控制流程的区别

今天进一步明确：

- `print()` 不会直接改变已经计算出的 `current_speed`；
- 读取 `current_speed` 属性，不代表重新进行了测速；
- 主循环频率、编码器采样频率和 PID 调节频率是不同的；
- 高频打印会增加系统负载，可能影响执行时机，但不代表一定会丢失 GPIO 中断；
- 应当在有意义的控制事件发生时输出调试信息，避免无条件地在高速循环中大量打印。

当前编码器的有效测速窗口约为 0.2 秒，控制器累计三次测速后执行一次 PID 调节，理论上的调节间隔约为 0.6 秒。

### 4. 初步观察转速稳定性

今日目标转速为 **90 RPM**。

启动阶段，转速数据约为 79–164 RPM；运行一段时间后，读数大多集中在约 88–94 RPM。

当前可以初步判断：

- 启动阶段存在较大波动；
- 后期转速相对稳定；
- 尚未完整验证左右轮在目标变化时的动态响应；
- 不能只凭这组读数判断所有工况下的控制质量。

## 四、长期有效的技术原则

1. **基线 → 对照 → 验证 → 修改。** 先保留已验证正常的版本，再进行小范围修改。
2. **重构应尽量保持原有行为。** 不要在封装代码的同时无意改变控制流程。
3. **调试输出也是系统负载的一部分。** 但不能把相关性直接当作已经证实的根因。
4. **先分析数据，再调整 PID。** 不根据单个瞬时读数盲目调参。
5. **先验证速度闭环，再接入摇杆。** 需要验证的不仅是固定目标下的稳定性，还有目标变化时的动态表现。
6. **避免无计划的重复调试。** 已经通过验证的硬件和代码不应反复折腾，除非新证据表明存在问题。
