一、今日主题

动态 PWM 偶发掉速至 0 的故障定位与修复；修复后重新验证 P 控制。

---

二、今日完成内容

1. 继续定位动态 PWM 偶发掉速故障

此前已经发现：

- 固定 PWM 长时间运行稳定，不会自行掉速。
- 动态改变 PWM 时，电机偶尔会突然掉速并最终变为 0 RPM。
- 更换为 DRV8870 后，该现象仍然存在，因此不能简单归因于原来的 ZK-BM1。
- 故障发生时，电池电压没有出现能够解释问题的明显异常。
- 故障发生时 DRV8870 的 OUT 输出为 0V。
- 进一步测量发现，故障发生时 ESP32 的 IN1 也为 0V。

因此继续检查 ESP32 PWM 实际状态。

---

2. 发现软件状态与实际 PWM 状态不一致

此前在动态 P 控制运行过程中记录到：

motor_speed ≈ 51
motor.pwm.duty_u16() = 0

也就是说：

软件中的 motor.speed：
约 51%

PWM 外设实际 duty：
0

此时电机自然失去驱动，随后编码器测速结果逐渐下降：

约 89 RPM
↓
约 70 RPM
↓
约 40 RPM
↓
约 17 RPM
↓
约 2 RPM
↓
0 RPM

因此已经可以确定：

«当时真正导致电机停转的是 PWM 实际输出变成了 0，而不是编码器单纯错误地报告 0 RPM。»

同时发现 "Motor.set_speed()" 中存在状态保护：

if speed == self.speed:
    return

因此如果软件认为当前速度已经是 51，而实际 PWM 已经异常变成 0，那么再次执行：

motor.set_speed(51)

时会直接 "return"，不会重新写入 PWM。

这能够解释为什么 PWM 一旦异常变成 0 后，电机不会自动恢复。

但这一条件本身不能解释“PWM 为什么第一次变成 0”，所以继续检查 PWM 设置过程。

---

3. 定位到 Motor.set_speed() 中的 PWM 切换逻辑

原来的正向 PWM 设置逻辑为：

if speed > 0:
    self.pwm1.duty_u16(0)
    self.pwm2.duty_u16(0)
    self.pwm1.duty_u16(int(speed_1/100*65535))

反向同样会先将两个 PWM 通道全部清零：

elif speed < 0:
    self.pwm1.duty_u16(0)
    self.pwm2.duty_u16(0)
    self.pwm2.duty_u16(int(speed_1/100*65535))

这意味着每一次动态调节 PWM，实际过程不是：

原 PWM
↓
新 PWM

而是：

原 PWM
↓
PWM1 = 0
PWM2 = 0
↓
重新设置目标 PWM

固定 PWM 时只需要设置一次，因此不会反复经过这个过程。

动态 PWM 则会不断重复这个过程。

---

4. 修改 PWM 切换逻辑

将同方向调速时的代码修改为只关闭另一方向的 PWM。

正向：

if speed > 0:
    self.pwm2.duty_u16(0)
    self.pwm1.duty_u16(int(speed_1/100*65535))

反向：

elif speed < 0:
    self.pwm1.duty_u16(0)
    self.pwm2.duty_u16(int(speed_1/100*65535))

停止时才同时关闭两个 PWM：

elif speed == 0:
    self.pwm1.duty_u16(0)
    self.pwm2.duty_u16(0)

这样同方向动态调速时不再经历：

PWM → 0 → 新 PWM

而是：

PWM → 新 PWM

---

5. 修复后进行动态 P 控制验证

修复后重新运行：

target_speed = 100 RPM
base_pwm ≈ 50
Kp = 0.1

运行过程中 PWM 大约在：

50.9% ～ 51.1%

之间变化。

实际转速长期保持在：

约 89 ～ 91 RPM

没有再次出现：

PWM duty = 0

也没有再次出现：

电机突然掉速 → 0 RPM

测试最终通过 "KeyboardInterrupt" 手动结束。

因此目前可以确认：

«修改 PWM 切换逻辑后，之前困扰多日的动态 PWM 偶发掉速故障在本轮长时间动态测试中消失。»

三、今日 P 控制结果

故障解决后，P 控制本身仍然表现出明显稳态误差。

当前：

目标速度 ≈ 100 RPM
base_pwm ≈ 50
Kp = 0.1

稳定运行时：

PWM ≈ 51%
实际速度 ≈ 89～91 RPM
误差 ≈ 9～11 RPM

例如：

实际速度 ≈ 90 RPM
error ≈ 10 RPM

PWM = base_pwm + Kp × error
    ≈ 50 + 0.1 × 10
    ≈ 51

因此系统会稳定在约 90 RPM：

90 RPM
↓
误差约 10
↓
PWM约51%
↓
约90 RPM
↓
误差仍约10

这属于 P 控制正常存在的稳态误差问题，而不是今天的硬件/PWM故障。

后续进入 I / PI 控制时再解决。

四、今天最重要的工程认识

1. 软件状态不等于硬件实际状态

今天最典型的情况：

motor.speed = 51

并不能证明：

PWM 外设实际输出 = 51%

必须通过：

motor.pwm.duty_u16()

等实际状态进行验证。

---

2. 故障排查应该逐层向下

本次故障最终通过：

电机转速
↓
驱动器输出 OUT
↓
驱动器输入 IN1
↓
ESP32 PWM 实际 duty
↓
Motor.set_speed()

逐层缩小范围。

最终不是靠猜测电机、驱动器或电池，而是定位到了具体的软件 PWM 操作。

---

3. 固定 PWM 和动态 PWM 的执行路径可能完全不同

固定 PWM：

设置一次
↓
持续运行

动态 PWM：

设置
↓
重新设置
↓
重新设置
↓
重新设置
……

因此：

«固定运行正常，并不能证明动态调速代码的状态切换逻辑没有问题。»

---

4. 状态变量需要与实际硬件状态保持一致

当前 "Motor" 类中的：

self.speed

表示的是：

«软件最后一次认为自己设置的速度。»

它不是：

«PWM 外设当前一定真实输出的速度。»

这一区别以后做更复杂的控制系统时非常重要。
